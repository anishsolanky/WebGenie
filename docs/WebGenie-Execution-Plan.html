0. How This Plan Works

Every phase below is a self-contained, visible deliverable — you never move to the next phase until the current one is coded and you've verified it works, including how it looks. Each phase is split into three parts:

LabelMeaning
Manual — YouSomething only you can do: creating accounts, clicking through a cloud console, copying an API key. Claude Code cannot do these for you.
Code — UsEverything else: scaffolding, installing packages, writing files, running dev servers. Done together in the coding session — Claude Code runs the terminal commands and writes the files directly.
Test — YouYou open the browser (and sometimes the database) and confirm the phase's checkpoint actually works, including how the UI looks and feels, before we move on.
Rule of thumb: if a step needs a browser tab open to a third-party website (MongoDB Atlas, OpenRouter) or a decision only you can make, it's Manual. If it's a terminal command or a file inside this repo, it's Code and happens in the session.

1. What WebGenie Is

A SaaS web app where a user types a prompt like "create a developer portfolio website" and the AI:

  1. Plans a file structure (which components the site needs)
  2. Generates each file's code in parallel, streaming progress to the UI in real time
  3. Renders the result live using Sandpack (an in-browser React sandbox, not a static preview)
  4. Lets the user manually edit code in Sandpack's built-in editor, or
  5. Continue chatting with the AI to revise the site (AI returns precise create/update/delete file operations, not a full rewrite)
  6. Export the project as a downloadable Vite+React zip, or Publish it read-only

Learning path this plan follows: Basic React Project → Pages/Routing → Login/Register UI → Home Page UI → Builder Page → Preview/Publish Page → Backend Server → Auth APIs → AI Build API → OpenRouter Integration → Agent Chat API → Full Integration.

3.1 — Component & Page Folder Convention

Every component and page is its own folder of exactly three files (a fourth only if genuinely needed — e.g. a page-local constants file):

ComponentName/ ├── ComponentName.tsx # component logic/JSX ├── ComponentName.styles.ts # named string constants — the ONLY place literal Tailwind classes live └── index.ts # export { default } from "./ComponentName";
// ComponentName.styles.ts
export const styles = {
  container: "flex items-center justify-between p-4 rounded-lg border border-border",
  title: "text-lg font-semibold text-ink-900",
} as const;

// ComponentName.tsx
import { styles } from "./ComponentName.styles";
<div className={styles.container}>
  <h2 className={styles.title}>{title}</h2>
</div>
Why this is a hard rule, not a style preference: Tailwind v4's scanner statically greps source files for complete class-name strings to decide what CSS to generate — it cannot resolve runtime interpolation. `text-${color}-500` silently produces no CSS for that class. So every string in a .styles.ts file must be a complete, literal class list. For a class that varies by prop/state, don't interpolate a fragment — pick between fully-written literal strings via a lookup map or function: 
const STATUS_COLOR: Record<Status, string> = {
  generating: "text-primary-600",
  completed: "text-ink-700",
  failed: "text-red-600",
};
export const styles = {
  badge: (status: Status) => `${STATUS_COLOR[status]} text-xs font-semibold`,
} as const;
The function's return value is computed at runtime, but every fragment it's built from is a complete literal the scanner can see somewhere in the file — that's what the scanner actually needs, not a static final string.

When a caller-supplied className needs to merge with a component's own classes, use the shared cn() helper (clsx + tailwind-merge, in utils/cn.ts) instead of string concatenation: className={cn(styles.container, className)}.

Shared/common classes stay in styles/index.css (§7's .btn-primary/.btn-secondary/.card/.input-field) — never duplicated per component. A component's own .styles.ts can reference them as literal strings alongside its component-specific classes, e.g. submitButton: "btn-primary w-full".

A component with no meaningful styling of its own (e.g. ProtectedRoute, a pure logic wrapper) skips .styles.ts entirely — don't create an empty file. If two pages end up duplicating the same non-trivial class strings (e.g. Login/Register share form styling), factor the shared ones into styles/shared.styles.ts and import from both — add this only once duplication actually shows up, not preemptively.

8. Verified Technical Notes & Gotchas

These were checked against current (Sept 2026) package behavior rather than assumed — keep them in mind as the relevant phase comes up.

React 18, not 19. npm create vite scaffolds React 19 by default, but @codesandbox/sandpack-react's peer deps top out at React 18 (the project is effectively unmaintained). Immediately after scaffolding in Phase 1: npm install react@18 react-dom@18.
Tailwind v4 has no config file. No tailwind.config.js, no PostCSS setup, no npx tailwindcss init. Just @tailwindcss/vite as a Vite plugin + @theme {} in CSS.
Sandpack's files prop expects {code}, not {content}. Our Mongo schema stores content; sandpackUtils.js must map between the two. Also put key={project.version} on SandpackProvider so every edit forces a clean remount (files aren't reliably reactive otherwise). Use template="react" (classic bundler) for the live preview — faster than vite-react for many small hot-swapped files.
Cross-origin cookies are fragile on localhost. Frontend (:5173) and backend (:8000) are different origins. Instead of fighting SameSite=None; Secure on plain HTTP, proxy both REST and WS through Vite's dev server so the browser only ever talks to :5173: 
// client/vite.config.js
server: {
  proxy: {
    '/api': { target: 'http://localhost:8000', changeOrigin: true },
    '/ws':  { target: 'ws://localhost:8000', ws: true },
  },
}
Then the cookie can simply be httponly=True, samesite="lax", secure=False for local dev.
instructor + OpenRouter: use the current, non-deprecated pattern: 
client = instructor.from_provider(
    f"openrouter/{settings.OPENROUTER_MODEL}",
    base_url="https://openrouter.ai/api/v1",
    api_key=settings.OPENROUTER_API_KEY,
    async_client=True,
)
result = await client.chat.completions.create(
    response_model=FilePlanSchema,
    messages=[...],
    extra_body={"provider": {"require_parameters": True}},
)
The extra_body line forces the routed free model to actually honor structured-output params — without it some free models silently ignore the schema.
Pin one exact free model id — never openrouter/free. That meta-router picks randomly among free models each call, which breaks a schema-constrained pipeline. Browse openrouter.ai/models, filter Free + Tool-calling, copy one id into .env as OPENROUTER_MODEL (Phase 0).
requirements.txt pins that prevent crashes: bcrypt==4.0.1 (newer bcrypt removed an attribute passlib reads, crashing on first hash/verify) and python-jose[cryptography]==3.3.0 (use the real crypto backend, not the pure-Python fallback).
Windows PowerShell venv activation. .\venv\Scripts\Activate.ps1 fails on a fresh machine with an execution-policy error. Run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass immediately before activating (process-scoped, no admin rights needed).
Install React Router explicitly as v6. Plain npm install react-router-dom grabs v7 by default; run npm install react-router-dom@6. It ships its own TypeScript types.
TypeScript scaffold + type packages. Use npm create vite@latest client -- --template react-ts (not react). After pinning React to 18, also install matching types: npm install -D @types/react@18 @types/react-dom@18. Sandpack and Axios ship their own types; file-saver does not, so add npm install -D @types/file-saver.
Redux Toolkit pattern. store/index.ts builds the store with configureStore and exports RootState/AppDispatch inferred from it. store/hooks.ts exports typed useAppDispatch/useAppSelector — components use these, never the raw untyped useDispatch/useSelector. Each domain gets its own slice (authSlice.ts, projectSlice.ts) built with createSlice + createAsyncThunk for API calls, so services/ stays plain request functions and the slice owns loading/error state.
Every component/page is a folder, not a flat file — see §3.1 for the full convention. In short: Name/Name.tsx + Name.styles.ts (named Tailwind class-string constants) + index.ts (re-export). Requires clsx + tailwind-merge for the shared cn() class-merge helper in utils/cn.ts.
